# MCP Gateway 技术架构方案（架构师视角）

> 技术栈：Vue3 + UnoCSS + TypeScript + NestJS + TypeORM + SQLite
> 内核约束：单进程 / 单 SQLite 文件 / fork 模式禁 cluster / 无 Redis·MQ·PG

---

## 二、NestJS 模块划分与治理链落点

| 层       | NestJS 概念                              | 落点                                                                                                                            |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 传输鉴权 | **Guard**                                | `ApiKeyGuard`（MCP 通道）、`AdminTokenGuard`（Admin 通道），两套完全隔离                                                        |
| 参数校验 | **Pipe / zod**                           | Admin API 入参用 zod schema + `ZodValidationPipe`                                                                               |
| 治理链   | **Service 显式编排**                     | 权限→限流→熔断→并发→转发 顺序**不可用拦截器隐式串**，必须在 `GatewayRouterService.routeCall()` 内显式按序调用，保证顺序不可调换 |
| 变更留痕 | **Interceptor**                          | `ChangeLogInterceptor` 对 Admin 写操作统一记录 before/after                                                                     |
| 审计落库 | **独立 Service + 队列**                  | 绝不进请求主链路同步写；`AuditService.log()` 只 push 内存数组                                                                   |
| 生命周期 | **OnModuleInit / OnApplicationShutdown** | 启动连上游、加载 fallback；退出 flush 审计、关上游、关库                                                                        |

> **关键取舍**：治理链不做成 5 个 Nest Interceptor。因为拦截器是「洋葱模型」，限流失败要短路返回、熔断失败要短路返回，用拦截器表达「顺序 + 短路 + 各自错误码」反而绕。用一个 `routeCall()` 方法顺序 `await` 每个 Service，语义最清晰、最易测试。

## 四、数据模型（TypeORM 实体，SQLite）

沿用原 PRD 9 张表，时间戳统一 `INTEGER` epoch ms：

`schema_migrations` · `settings` · `upstreams` · `tools_snapshot` · `tool_overrides` · `roles` · `role_rules` · `api_keys` · `audit_logs` · `change_logs`

**审计索引以「安全部门的问题」为设计输入**（每条问句一条索引）：ts / (user_name,ts) / (tool,ts) / (upstream,ts) / (sensitive,ts) / (key_id,ts) / request_id。

**三条落地纪律**：

1. **异步攒批写**：TypeORM 同步性不阻塞事件循环的说法在 SQLite 下仍需谨慎——审计走内存队列 + `setInterval(1000)`/满 100 条触发单事务批量 insert；退出先 flush 再关；flush 失败 append 到 `data/audit-fallback.jsonl`，启动回放。
2. **敏感分级**：上游 `sensitivity='high'` ⇒ 全部调用记 `args_full` 且 `sensitive=1`；其余仅摘要。
3. **只增不改**：代码层不提供 audit 的 UPDATE/DELETE 业务路径；归档任务分批 DELETE（每批 5000、批间 sleep 50ms）。

## 五、治理算法（TypeScript 实现要点）

### 5.1 RBAC：通配符 + 顺序匹配 + 默认拒绝

- `toRegex(pattern)` 预编译缓存 `Map<pattern, RegExp>`（600 工具 × 20 规则不能每次 `new RegExp`）。
- `firstMatch(rulesSorted, name)` 按 sort 升序首条命中即决定；无命中 = 拒绝。
- `buildAllowedSet()` 结果按 `(role, registryVersion)` 缓存，TTL 60s；三条件失效：版本变化/规则更新/TTL 到期。
- **list 与 call 共用同一份 allowedSet**（可见即可调契约）。

### 5.2 令牌桶限流

- `take(keyId, tool, rate, capacity)`；桶键 `keyId|tool`。
- **sweep 回收**：桶数 = Key × 工具可达 30 万，必须清陈旧桶（idle > 10min）。
- 多实例语义：内存桶是每进程的，一期只允许单实例；扩展换 SqliteRateLimiter 或 Redis Lua。

### 5.3 三态熔断

- closed →（窗口内连续失败 ≥ 5）→ open（快速失败）→（冷却 60s）→ half-open（放 1 个探针）→ 成功回 closed。
- **错误分类**：`BAD_ARGS`/`FORBIDDEN` 属客户端问题，**不计入熔断**（否则传错参数即可熔掉上游，是可用性攻击路径）。
- 探针只放一个（`probing` 布尔位独占）。

### 5.4 上游并发信号量

- 每上游一个 `Semaphore(limit, maxQueue)`；`queue_ms` 记入审计识别慢上游排队。

### 5.5 错误归一化

- 上游千奇百怪的错收敛为 `[错误码] 简短中文`；`isError:true`（工具业务失败）而非 JSON-RPC error。
- `safeMessage()`：剥离堆栈、内网 IP/端口、SQL 片段、绝对路径，截断 200 字符——**这是安全边界**。

## 六、会话与传输层（落地最大分歧点）

- **事实**：`StreamableHTTPServerTransport` 与 `McpServer` 持有协议状态；SDK 官方示例用进程内 `Map<sessionId, transport>`。
- **一期结论**：单实例 + 有会话。`ecosystem.config.cjs` fork 模式 `instances:1`。
- 会话内存上限 `maxSessions`(300)、`idleTimeout`(30min)，`setInterval(60_000)` 回收；超限拒绝新 `initialize` 返回 503。
- `caller` 在 initialize 绑定并随会话固定（避免中途换 Key 权限漂移），但**吊销检查每次执行**（60s 鉴权缓存）保证 US-07 ≤10s 生效。
- NestJS 集成：`/mcp` 用原生 `@Req() @Res()` 拿到 Express req/res 交给 SDK transport，不走 Nest 的 body 解析（需 `rawBody`）。

## 七、安全边界（逐条可验证）

| 风险        | 控制                                                                                                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API Key     | `randomBytes(24)` base64url + 前缀 `mgw_live_`；只存 SHA-256；明文仅签发响应出现 1 次                                                                         |
| 上游凭据    | AES-256-GCM(`iv12\|tag16\|ct` base64)，主密钥来自 `MGW_SECRET(_FILE)`，不入库不进 git                                                                         |
| Admin Token | `crypto.timingSafeEqual` 防时序侧信道；与 MCP Key 两套前缀、两套校验、代码路径互不可达                                                                        |
| SQL 注入    | 全参数绑定；仅数字/白名单枚举可拼 SQL                                                                                                                         |
| ReDoS       | pattern 编译前检测长度与嵌套量词（拒绝 `(a+)+`）                                                                                                              |
| SSRF        | 上游 URL 协议限 http/https；默认 `blocklist` 阻断回环/私网/链路本地/云元数据、公网放行，支持 `allowlist` 收紧；DNS 解析后二次校验；云元数据永久拒绝；禁重定向 |
| Shell 注入  | stdio `spawn(cmd, argsArray)`，`shell:false`，凭据走 env 不拼命令串                                                                                           |
| PII 泄漏    | `redact` 入库前对 args_digest/args_full/error_msg 掩码，置 `redacted=1`                                                                                       |
| 请求体膨胀  | body limit 1mb；工具返回超 5MB 截断                                                                                                                           |

## 八、可观测性与部署

- `/healthz`：进程 + 库可写 + 上游概览，**不探测上游**（O(1)）。
- `/metrics`：JSON（可选 Prometheus 文本），现有监控拉取。
- 日志：单行 JSON 到 **stderr**（MCP 纪律：stdout 是协议通道），禁 `console.log`。
- IM webhook：熔断/恢复事件推钉钉/企微/飞书，含 5 分钟同类抑制。
- 部署：pm2（fork 禁 cluster，max_memory_restart 1200M）或 Docker（node:22-bookworm-slim，非 root，data 挂卷）；Nginx `proxy_buffering off` + `read_timeout 300s`（SSE 必配）。

---

## 九、扩展预埋点（一期就必须写对）

1. **Repository 抽象**：SQL 只在数据层，换 PG 只改这一层 + `?`→`$1`。
2. **限流/熔断后端可插拔**：构造注入 `memory|sql|redis`，一期交付 memory + sql。
3. **会话状态最小化**：会话只放协议必需项，caller 可从 Key 重建，外置时序列化一小段 JSON。

## 十、前端架构（Vue3 + UnoCSS）

- **状态**：Pinia 分域 store（auth/upstream/tools/permission/key/audit/change/report）。
- **请求**：axios 实例统一注入 `Authorization: Bearer <ADMIN_TOKEN>`、401 跳登录、错误 toast。
- **路由守卫**：无 token 跳 `/login`；按角色（Admin/Auditor/Owner）控制菜单与页面可见性。
- **主题**：`uno.config.ts` 定义 `glass` / `glass-dark` 快捷类 + CSS 变量色板；`useTheme()` 切换深浅色，持久化 localStorage。
- **组件**：`GlassCard`（毛玻璃容器）、`DataTable`（高密度表格 + 分页）、`StatusTag`（语义色状态）、`ConfirmDialog`（变更预览）。
- **图表**：报表用轻量 SVG/CSS 条形，不引 ECharts（保持轻量），必要时按需引 `echarts` tree-shake。
